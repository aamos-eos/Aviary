# Battery Model

This directory contains the Atlas battery model, designed to simulate the performance of a multi-string battery pack. It handles power distribution, state-of-charge (SOC) tracking, and thermal calculations, with support for over-discharge scenarios through robust clipping logic.

## Components Overview

The core of the battery model is the `EmpiricalBatteryPower` group (in `battery_empirical_power.py`), which connects several sub-components to form a complete system:

1.  **DemandFeed (`cross_feed_logic.py`)**:
    *   Distributes the total electric power demand from motors to the individual battery strings.
    *   Supports different feeder modes (e.g., independent, cross-feed) to handle how power is shared.

2.  **BatteryPower (`battery_empirical_power.py`)**:
    *   Calculates the battery and cell-level power based on the demand, auxiliary loads, and power architecture efficiency (`eta_parc`).
    *   Converts pack-level power to cell-level power for interpolation.

3.  **BatteryMMInterpolationGroup (`battery_mm_interpolation_group.py`)**:
    *   The "brain" of the performance model. It uses structured metamodels (`MetaModelStructuredComp`) to interpolate **Line Voltage** and **Current** based on the current **SOC** and **Power**.
    *   Loads training data from a CSV database generated by `build_battery_database.py`.
    *   **Crucially**, it includes limits on current to ensure the interpolation remains within the bounds of the training data.

4.  **SOCLimiter / Clipping Logic**:
    *   To handle cases where the battery might over-discharge (SOC < 0) or over-charge (SOC > 1) during a solver iteration or a mission profile, the model employs **smooth clipping**.
    *   `SmoothMaxComp` and `SmoothMinComp` (from `aviary.utils.smooth_minmax`) are used to constrain inputs like SOC and Voltage.
    *   **SOC Clipping**: The SOC used for interpolation is clipped between specific bounds (e.g., `1e-3` to `1.0`) before being passed to the interpolators. This ensures that even if the integrator computes a negative SOC, the performance lookup asks for the value at the minimum valid SOC, preventing solver crashes or `NaN`s from extrapolation.

5.  **UpdateCellState (`battery_empirical_power.py`)**:
    *   Calculates the rates of change for state variables, primarily `dsoc_dt` (rate of change of SOC) and thermal derivatives (`dT_dt`).
    *   Computes efficiency and heat generation based on the difference between Open Circuit Voltage (OCV) and Line Voltage.

6.  **Integrators (`IntegrateMissionSOC`)**:
    *   Integrates `dsoc_dt` over time to track the SOC profile throughout the mission phases.
    *   Handles multi-phase missions by chaining integrators and ensuring continuity of SOC between phases.

## Logic for Over-Discharge (Clipping)

A key feature of this model is its robustness in "dead battery" scenarios. When a mission requires more energy than the battery holds, a standard model might drive SOC negative, causing lookup tables to fail. This model handles it as follows:

1.  **SOC Integration**: The integrator calculates the "true" physical SOC, which can technically go negative if power is drawn for too long.
2.  **Clipping for Interpolation**: Before this SOC is used to look up voltage or current, it is passed through `limit_min_soc` (SmoothMax) and `limit_max_soc` (SmoothMin).
    *   `soc_clipped = SmoothMin(SmoothMax(soc, soc_min), soc_max)`
    *   This `soc_clipped` is strictly within `[0, 1]`.
3.  **Performance Lookup**: The interpolators (`ocv_interp`, `line_voltage_interp`, `current_interp`) use `soc_clipped`.
    *   If the battery is dead (SOC < 0), the model simulates it as being at `soc_min`.
    *   This returns a valid low voltage and high current, allowing the solver to converge mathematically, even if the mission is physically infeasible (which the optimizer can then penalize).

## Data Flow

1.  **Inputs**: `p_train_elec` (Motor Power), `p_aux_elec` (Aux Loads), `dt` (Time steps).
2.  **Power Calculation**: Power is distributed to strings -> `p_bat` -> `p_cell`.
3.  **State Limiting**: Current `SOC` state is clipped to valid bounds.
4.  **Interpolation**: `p_cell` and `soc_clipped` -> `vline_cell`, `i_cell`, `ocv_cell`.
5.  **State Rates**: `i_cell` -> `dsoc_dt`, `heat`.
6.  **Integration**: `dsoc_dt` -> New `SOC` for next step.

## Usage

To use this model in an aircraft simulation:
1.  Instantiate `EmpiricalBatteryPower` with the number of nodes and strings.
2.  Provide the required inputs (power demand, battery configuration).
3.  Ensure `build_battery_database.py` has been run to generate the necessary CSV data files for interpolation.
